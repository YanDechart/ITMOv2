# Few-shot

- Артефакт Практики 1: practices/practice_01/adr.md
- Что хотим улучшить: явное соблюдение правила QA-1 — в разделе «Решение» отсутствует явная проверка, что каждый риск подтверждён строкой diff или правилом репозитория; есть риск попадания неподтверждённых рисков.

## Вход и цель

- Вход: текущий practices/practice_01/adr.md, CASE.md (правило QA-1), контекст Практики 1.
- Цель: предложить минимальную правку ADR, чтобы чётко обеспечить QA-1 без добавления новых требований.

## Примеры

### Хороший результат

1) Требование → Решение → Evidence → Последствие
   - Требование: QA-1 — риск включается в ответ, только если подтверждён строкой diff или правилом репозитория (CASE.md).
   - Решение: перед возвратом валидировать, что каждый элемент `risks` содержит `evidence` и указывает на строку diff или правило; иначе элемент исключается.
   - Evidence: CASE.md: «QA-1: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.»
   - Последствие: в ответ не попадут неподтверждённые риски; проверки воспроизводимы.

2) Требование → Решение → Evidence → Последствие
   - Требование: OUT-1 — не более трёх рисков c полями `file`, `line`, `evidence`, `risk`.
   - Решение: схема ответа валидируется и обрезается до ≤3 рисков.
   - Evidence: CASE.md: «OUT-1: … В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.»
   - Последствие: стабильный контракт для автоматических проверок.

3) Требование → Решение → Evidence → Последствие
   - Требование: SEC-1 — перед отправкой в LLM удалить секреты.
   - Решение: редактирование секретов в diff с заменой значений на [REDACTED].
   - Evidence: CASE.md: «SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.»
   - Последствие: снижение риска утечек.

### Плохой результат

Решение: увеличим лимит `risks` до 5 и добавим свободный текст «обоснование».
Почему плохо: не подтверждено требованиями; противоречит OUT-1 (≤3, фиксированные поля).

## Реально использованный prompt

Роль: AI assistant for architecture review.

Задача: по коротким примерам «требование → решение → evidence → последствие» проверь текущий practices/practice_01/adr.md и предложи ровно одно улучшение, строго вытекающее из правил CASE.md и контекста Практики 1. Не добавляй новых требований. Если ADR уже покрывает требование, не предлагай правку.

Ожидание: если найден пробел по QA-1, предложи минимальную правку в разделе «Решение»: явная валидация, что каждый `risk` подтверждён строкой diff или правилом; иначе элемент не включается.

## Наблюдаемый результат

Наблюдение: ADR перечисляет OUT-1 (структура ответа), но не фиксирует механизм соблюдения QA-1. Это риск появления неподтверждённых рисков в ответе. По хорошим примерам решение должно явно включать валидацию `risks` на наличие подтверждения из diff или правила.
