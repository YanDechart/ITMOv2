# Feature Specification: Mini My ITMO — Schedule Logic

**Feature Branch**: `[002-mini-myitmo-logic]`

**Created**: 2026-11-01

**Status**: Draft

**Input**: User description: "Разработай первую независимую спецификацию логики расписания для Mini My ITMO — минимального веб-сайта личного кабинета студента ИТМО. Приложение должно предоставлять демонстрационные данные студента (имя, учебная группа), расписание занятий на неделю; данные о занятиях: предмет, время начала и окончания, аудитория, преподаватель; возможность получать расписание для выбранного дня; корректную обработку дней без занятий; обработку ошибок загрузки и некорректных данных; возможность повторного запроса после ошибки. Без авторизации, реального API и БД; локальные демонстрационные данные."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр расписания на выбранный день (Priority: P1)

Студент хочет увидеть список занятий на выбранный день недели на основе локальных демонстрационных данных.

**Why this priority**: Это базовая ценность расписания — быстро получить список занятий на день.

**Independent Test**: Загрузить демо-данные, запросить расписание для дня (например, понедельник), убедиться в корректной сортировке по времени и корректной обработке пустых дней.

**Acceptance Scenarios**:

1. Given демо-данные успешно загружены, When пользователь запрашивает день с занятиями, Then система возвращает список занятий, отсортированный по времени начала по возрастанию, с полями: предмет, время начала/окончания, аудитория, преподаватель.
2. Given демо-данные успешно загружены, When пользователь запрашивает день без занятий, Then система возвращает пустой список и явный статус/причину "нет занятий в этот день" без ошибок.
3. Given несколько занятий с одинаковым временем начала, When список формируется, Then применяется детерминированная вторичная сортировка (по времени окончания, затем по предмету, затем по аудитории).

### User Story 2 - Повторная попытка после ошибки загрузки (Priority: P2)

Если загрузка или валидация данных завершилась ошибкой, студент/клиентский интерфейс может повторить попытку, когда проблема устранена.

**Why this priority**: Обеспечивает устойчивость к сбоям и возможность восстановления без перезапуска приложения.

**Independent Test**: Смоделировать ошибку загрузки или валидации (например, отсутствует файл данных или неверный формат времени), проверить, что система сообщает тип ошибки и позволяет выполнить повторный запрос; после корректировки данных повторная попытка приводит к успешной загрузке.

**Acceptance Scenarios**:

1. Given источник демо-данных недоступен, When выполняется загрузка, Then возвращается ошибка типа LoadError с кодом DATA_UNAVAILABLE и описанием.
2. Given ошибка загрузки произошла, When выполняется повторный запрос после восстановления источника, Then данные успешно загружаются и становятся доступны для запросов по дням.
3. Given демо-данные содержат некорректные значения (например, start_time >= end_time), When выполняется валидация, Then возвращается ValidationError с указанием поля/записи; When данные исправлены и выполнен повторный запрос, Then загрузка проходит успешно.

### User Story 3 - Просмотр расписания на неделю (Priority: P3)

Студент хочет увидеть полное расписание на неделю с группировкой по дням недели.

**Why this priority**: Полезно для планирования недели, но вторично по сравнению с ежедневным просмотром.

**Independent Test**: Загрузить демо-данные, запросить недельное расписание, убедиться, что возвращено 7 дней, каждый день содержит отсортированный список занятий, а пустые дни помечены корректным состоянием.

**Acceptance Scenarios**:

1. Given демо-данные успешно загружены, When запрашивается недельное расписание, Then возвращается структура из 7 дней (Пн–Вс) с отсортированными занятиями.
2. Given часть дней без занятий, When возвращается неделя, Then пустые дни представлены пустым списком с явным признаком "нет занятий".

### Edge Cases

 - В день все занятия пересекаются по времени: сортировка сохраняется по началу, пересечения допускаются; пересечения не считаются ошибкой, но фиксируются для UI (см. раздел Validation в Business Rules).
- Дубликаты занятий в один и тот же интервал: допускается, возвращается как есть; UI может объединять/подсвечивать (решение за UI).
- Неверные поля: пустое имя предмета, пустой преподаватель, пустая аудитория — считаются ошибкой валидации.
- Формат времени не по 24-часовому формату HH:MM — ошибка валидации.
- Запрос расписания по некорректному дню (вне Пн–Вс) — ошибка INVALID_DAY.
- Неделя с количеством дней ≠ 7 — ошибка DATA_FORMAT.

## Requirements *(mandatory)*

### Functional Requirements

- FR-001: Система ДОЛЖНА предоставлять локальные демонстрационные данные студента: имя (строка, не пустая) и учебная группа (строка, не пустая).
- FR-002: Система ДОЛЖНА предоставлять локальное недельное расписание (ровно 7 дней; неделя Понедельник–Воскресенье по ISO-8601, Пн=1, …, Вс=7).
- FR-003: Система ДОЛЖНА предоставлять операции получения: (a) данных студента, (b) полного недельного расписания, (c) расписания для выбранного дня по ключу дня.
- FR-004: Система ДОЛЖНА корректно обрабатывать дни без занятий: возвращать пустой список занятий и явно помечать состояние дня как "нет занятий" без ошибок.
- FR-005: Система ДОЛЖНА сортировать занятия внутри дня по времени начала по возрастанию; при равенстве применять вторичную сортировку по времени окончания, затем по названию предмета (лексикографически), затем по аудитории.
- FR-006: Система ДОЛЖНА валидировать данные при загрузке: обязательные поля (предмет, start_time, end_time, аудитория, преподаватель) должны быть непустыми; время в формате HH:MM (00:00–23:59); start_time < end_time; день недели валиден (1–7).
- FR-007: Система ДОЛЖНА различать и возвращать типы ошибок: LoadError (источник недоступен), DataFormatError (структура/схема неверна), ValidationError (значения неверны), DomainError (ошибки доменного ввода, напр. неверный день), UnknownError.
- FR-008: Система ДОЛЖНА обеспечивать возможность повторного запроса (retry) после любой ошибки, сбрасывая состояние ошибки на результат новой попытки.
- FR-009: Система ДОЛЖНА быть независимой от авторизации и внешних API; все данные — локальные демонстрационные.
- FR-010: Система ДОЛЖНА позволять UI определить текущий статус: "готово", "загрузка", "ошибка" (с типом/кодом), "пустой день".

### Key Entities *(include if feature involves data)*

- Student: описывает студента; атрибуты: name (строка), group (строка).
- ClassSession: занятие; атрибуты: subject (строка), start_time (HH:MM), end_time (HH:MM), room (строка), teacher (строка).
- DaySchedule: день недели; атрибуты: day_id (целое 1–7, ISO-8601), label (строка, локализуемая подпись дня), sessions (список ClassSession), is_empty (булево, выводимое из sessions == []).
- WeekSchedule: неделя; атрибуты: days (ровно 7 элементов DaySchedule в порядке 1→7), meta (опциональные атрибуты, например неделя № или период действия — не используется логикой v1).
- Error: типизированная ошибка; атрибуты: type (LoadError|DataFormatError|ValidationError|UnknownError), code (например DATA_UNAVAILABLE, INVALID_DAY, INVALID_TIME_FORMAT, START_NOT_BEFORE_END), message (человеко-понятное описание), details (опционально: указание поля/дня/записи).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- SC-001: В 95% запросов расписания для дня результат возвращается менее чем за 1 секунду при наличии демо-данных.
- SC-002: 100% списков занятий внутри дня отсортированы по правилам, указанным в FR-005.
- SC-003: 100% пустых дней возвращаются как пустые списки без ошибок (см. FR-004).
- SC-004: При возникновении ошибок 100% случаев содержат корректно классифицированный тип и код ошибки (см. FR-007), и повторный запрос очищает предыдущее состояние ошибки.
- SC-005: Не менее 90% пользователей (по наблюдениям на демо) успешно находят расписание на выбранный день без инструкции.

## Assumptions

- Неделя определяется как Понедельник–Воскресенье (ISO-8601). Локаль и названия дней определяются UI.
- Часовой пояс — локальный для среды выполнения; времена трактуются как минуты от полуночи соответствующего дня.
- Пересекающиеся занятия допустимы и не считаются ошибкой (расписание может содержать потоки/подгруппы).
- Преподаватель и аудитория обязательны для демо-данных v1.
- UI самостоятельно решает формат отображения времени, пустых дней и ошибок; логика предоставляет только значения и статусы.

### Business Rules: Retrieval, Validation, Sorting

1. Retrieval:
   - По умолчанию первая загрузка подготавливает Student и WeekSchedule из локального источника.
   - Получение по дню: вход — day_id (1–7) или дата, уже нормализованная до day_id UI-слоем; логика принимает day_id.
2. Validation:
   - Студент: name и group непустые строки.
   - Неделя: 7 дней; day_id уникальны, 1–7 без пропусков.
   - Занятия: все обязательные поля присутствуют; время в формате HH:MM; start_time < end_time.
3. Sorting:
   - Сортировка: start_time ASC, при равенстве — end_time ASC, затем subject ASC (кейз-инсенситив), затем room ASC.
4. Empty days:
   - Если sessions пуст, is_empty = true; это не ошибка.
5. Errors & Retry:
   - Любая ошибка возвращается с type+code+message.
   - Повторный запрос полностью переинициализирует внутреннее состояние данных из текущего источника.

### Exposed Operations for UI

- op_init_demo(): инициализировать и/или перезагрузить демо-данные (Student, WeekSchedule); возвращает статус загрузки или ошибку.
- op_get_student(): вернуть Student.
- op_get_week(): вернуть WeekSchedule (7 дней с сортированными sessions).
- op_get_day(day_id): вернуть DaySchedule по ISO day_id (1–7). При неверном значении — ошибка INVALID_DAY.
- op_retry(): синоним op_init_demo() — выполняет повторную попытку после ошибки.
- op_status(): вернуть текущее состояние: ready | loading | error (с типом/кодом) | empty-day (для последнего get_day).

### Error Catalogue (non-exhaustive)

- LoadError / DATA_UNAVAILABLE — источник демо-данных недоступен.
- DataFormatError / INVALID_DAY_STRUCT — структура дней не соответствует требованиям (не 7, неверные day_id).
- ValidationError / INVALID_TIME_FORMAT — время не HH:MM.
- ValidationError / START_NOT_BEFORE_END — start_time >= end_time.
- ValidationError / MISSING_FIELD — обязательное поле отсутствует (указывается details).
- DomainError / INVALID_DAY — запрошен день вне 1–7.

### Open Questions to UI (for alignment before implementation)

1. Формат day selector: UI будет передавать day_id (1–7) или дату (YYYY-MM-DD), которую логика должна парсить? В спецификации логики выбран вариант принимать day_id (1–7). Подтвердить.
2. Локаль названий дней: нужны ли локализованные label от логики или UI сам локализует?
3. Поведение при пересечениях занятий: UI ожидает подсветку/агрегацию пересечений или достаточно упорядоченного списка?
4. Представление статусов: требуется ли отдельный статус для "нет занятий" или UI будет определять по пустому списку?
