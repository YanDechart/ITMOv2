# Mini My ITMO — UI ↔ Logic CONTRACT (Practice 05)

Status: Draft for alignment
Date: 2026-11-01
Scope: согласованный контракт между UI и логикой для Mini My ITMO (демо с локальными JSON-данными; HTML/CSS/vanilla JS).

## 1. Общие принципы

- Источник данных: локальные демо-данные (без API и авторизации).
- Асинхронность: все операции логики возвращают Promise и могут резолвиться/реджектиться с задержкой (симуляция загрузки).
- Единица навигации: дни недели текущей учебной недели (без абсолютных дат). UI маркирует «Сегодня» по локальному времени.
- Ответственность: логика отвечает за валидацию и сортировку; UI отвечает за отображение и состояния.

## 2. Структуры данных (camelCase)

- Student
  - name: string (required, non-empty)
  - group: string (required, non-empty)

- Lesson
  - subject: string (required, non-empty)
  - startTime: string (HH:MM, 24h, required)
  - endTime: string (HH:MM, 24h, required; must be > startTime)
  - room?: string (optional; if отсутствует или пустой — UI отображает «—»)
  - teacher?: string (optional; если отсутствует или пустой — UI отображает «—»)

- DaySchedule
  - dayId: number (1–7, ISO-8601: Mon=1 … Sun=7)
  - label: string (например, «Пн», «Вт»; предоставляется логикой по умолчанию, но UI может локализовать самостоятельно)
  - lessons: Lesson[] (отсортировано; может быть пустым)
  - isEmpty: boolean (истина, если lessons.length === 0)

- WeekSchedule
  - days: DaySchedule[] (ровно 7 элементов, в порядке 1→7)
  - meta?: object (необязательные метаданные; не используются в v1)

- ErrorObject
  - type: 'LoadError' | 'DataFormatError' | 'ValidationError' | 'DomainError' | 'UnknownError'
  - code: string (см. каталог ошибок ниже)
  - message: string (человекочитаемое резюме)
  - details?: any (необязательно, для отладки/подсказок)

Примечание: Мы выбрали единый camelCase для полей, чтобы совпасть с ожиданиями UI и упростить работу в vanilla JS. Логика использует те же имена.

## 3. Формат дня недели

- Идентификатор дня: dayId: 1–7 (ISO-8601), Mon=1 … Sun=7.
- Метка дня: label: короткое имя ('Пн', 'Вт', 'Ср', 'Чт', 'Пт', 'Сб', 'Вс').
- Абсолютные даты (YYYY-MM-DD) в v1 не используются. UI помечает «Сегодня», сопоставляя dayId с локальным днём недели. Отображение календарной даты опционально и вне контракта v1.

## 4. Операции логического модуля (асинхронные)

Все функции возвращают Promise.

- init(): Promise<void>
  - Назначение: загрузить/переинициализировать демо-данные (Student, WeekSchedule).
  - Успех: resolve()
  - Ошибка: reject(ErrorObject)

- getStudent(): Promise<Student>
  - Возвращает Student. Предполагается, что init() уже был вызван.

- getWeek(): Promise<WeekSchedule>
  - Возвращает всю неделю (7 DaySchedule, отсортированных внутри).

- getDay(dayId: number): Promise<DaySchedule>
  - Вход: целое 1–7. Иной ввод — ошибка DomainError/INVALID_DAY.
  - Возвращает: DaySchedule для указанного dayId.

- retry(): Promise<void>
  - Синоним init(); используется UI в состоянии ошибки для повторной попытки.

Примечание: UI может вызывать getStudent() и getDay() параллельно после init(); порядок не требуется.

## 5. Состояния UI и соответствие ответам логики

- loading: показ при любом незавершённом Promise init()/getDay()/getWeek()/retry().
- success: показ, когда getDay() резолвится с lessons.length > 0.
- empty: показ, когда getDay() резолвится с lessons.length === 0 (isEmpty = true).
- error: показ, когда любая операция реджектится с ErrorObject.

UI не требует отдельного статуса «empty-day» от логики — определяется по пустому массиву lessons.

## 6. Коды ошибок и маппинг сообщений UI

Каталог кодов (минимальный набор):
- LoadError
  - DATA_UNAVAILABLE — источник демо-данных недоступен/не найден.
- DataFormatError
  - INVALID_DAY_STRUCT — структура недели неверна (не 7 дней, дубли или пропуски dayId).
- ValidationError
  - INVALID_TIME_FORMAT — время не HH:MM.
  - START_NOT_BEFORE_END — startTime >= endTime.
  - MISSING_FIELD_SUBJECT — отсутствует subject.
  - MISSING_FIELD_START_TIME — отсутствует startTime.
  - MISSING_FIELD_END_TIME — отсутствует endTime.
- DomainError
  - INVALID_DAY — dayId вне диапазона 1–7.
- UnknownError
  - UNKNOWN — непредвиденная ошибка.

UI отображает:
- Для LoadError/DataFormatError/UnknownError: «Не удалось загрузить расписание. Повторите попытку.»
- Для ValidationError: «Некорректные данные расписания.» (детали могут быть отображены в dev-режиме)
- Для DomainError/INVALID_DAY: «Выбран неверный день.»

## 7. Сортировка и валидация

- Сортировка выполняется логикой: по startTime ASC; при равенстве — endTime ASC; затем subject ASC (case-insensitive); затем room ASC (пустые в конце).
- UI доверяет порядку из логики. Fallback: если порядок нарушен, UI может пересортировать по startTime ASC.
- Валидация в логике: обязательны subject, startTime, endTime; проверка формата времени и того, что startTime < endTime. Поля room и teacher считаются опциональными (см. раздел «Обязательность полей» ниже).

## 8. Обязательность и обработка пустых/необязательных полей

- subject, startTime, endTime — обязательные.
- room, teacher — опциональные. Если отсутствуют или пустые, не считается ошибкой; UI показывает «—».
- Пустой день: lessons: [], isEmpty: true. Это корректное состояние, не ошибка.

## 9. Поведение Retry

- Кнопка «Повторить» вызывает retry() → затем (при успехе) повторно вызывает getDay(currentDayId).
- UI возвращается в loading на время retry() и последующего getDay().
- При успехе отображается success или empty; при повторной ошибке — снова error.

## 10. Быстрое переключение дней (concurrency)

- Политика latest-wins: UI присваивает каждому вызову getDay() внутренний requestId; по завершении обрабатывается только ответ последнего активного запроса; устаревшие ответы игнорируются.
- UI может отменять предыдущие незавершённые запросы (если логика поддержит AbortController); в v1 достаточно игнорирования устаревших ответов.

## 11. Пересечения занятий

- Пересечения (overlaps) допустимы и не являются ошибкой. UI отображает упорядоченный список без дополнительной визуальной логики в v1.

## 12. Минимальные примеры

Успешный день (есть занятия):
```
{
  "dayId": 1,
  "label": "Пн",
  "lessons": [
    { "subject": "Алгебра", "startTime": "08:30", "endTime": "10:00", "room": "Ауд. 101", "teacher": "Иванов И.И." },
    { "subject": "Физика", "startTime": "10:20", "endTime": "11:50", "room": "Ауд. 202", "teacher": "Петров П.П." }
  ],
  "isEmpty": false
}
```

Пустой день:
```
{
  "dayId": 7,
  "label": "Вс",
  "lessons": [],
  "isEmpty": true
}
```

Ошибка (пример DomainError):
```
{
  "type": "DomainError",
  "code": "INVALID_DAY",
  "message": "Day id must be between 1 and 7"
}
```

## 13. Таблица разногласий и итоговые решения

- Формат сущностей Lesson/Day/Week/Student
  - UI: Lesson.startTime/endTime; lessons[]; ScheduleDay: date + weekdayLabel.
  - Logic: start_time/end_time; sessions[]; DaySchedule: day_id + label.
  - Решение: единый camelCase; fields: startTime/endTime; коллекция lessons; DaySchedule: dayId + label + isEmpty. Причина: унификация под потребности UI и простота в vanilla JS.

- Способ получения профиля и расписания
  - UI: вопросы по источнику/моменту; допускает совместную или отдельную загрузку.
  - Logic: init() загружает Student и Week; отдельные getStudent/getWeek/getDay.
  - Решение: init() + отдельные getStudent/getDay/getWeek; UI может вызывать независимо. Причина: гибкость и простота демо.

- Формат идентификатора дня
  - UI: склоняется к абсолютной дате (вопрос открыт).
  - Logic: day_id 1–7 (ISO-8601).
  - Решение: dayId 1–7. Причина: стабильность демо и отсутствие привязки к календарю.

- Обязательность преподавателя и аудитории
  - UI: допускает отсутствие; отображает «—».
  - Logic: требовал обязательность (валидация).
  - Решение: сделать room/teacher опциональными; невалидны только subject/start/end. Причина: в реальности данные могут быть неполными; UI уже предусмотрел graceful degradation.

- Где выполняется сортировка
  - UI: готов сортировать; FR-005 «UI MUST сортировать».
  - Logic: сортирует и задаёт правила вторичной сортировки.
  - Решение: сортировку выполняет логика; UI доверяет порядку, но может пересортировать как fallback. Причина: единое правило в одном месте.

- Представление пустого дня
  - UI: состояние Empty.
  - Logic: lessons: [] + is_empty true; опциональный статус empty-day.
  - Решение: lessons: [] и isEmpty: true; отдельный статус не требуется. Причина: упрощение и согласованность с UI состояниями.

- Ошибки и их отображение
  - UI: единое сообщение «ошибка получения расписания», с возможной дифференциацией.
  - Logic: типы/коды ошибок подробные.
  - Решение: логика возвращает тип/код; UI маппит на несколько простых сообщений (см. раздел 6). Причина: простота UI и диагностическая ценность кодов.

- Повторная загрузка (Retry)
  - UI: кнопка «Повторить» перезапускает загрузку текущего дня.
  - Logic: op_retry/op_init_demo.
  - Решение: retry() = init(); затем getDay(currentDayId). Причина: простая модель без скрытого состояния.

- Быстрое переключение дней
  - UI: ожидание корректной работы при быстрой смене.
  - Logic: не регламентировано.
  - Решение: политика latest-wins на стороне UI; логика может оставаться «тупой». Причина: избегаем сложной отмены в логике.

- Пересечения занятий
  - UI: отображает как есть; не решает.
  - Logic: допускает, сортирует.
  - Решение: оставить как есть; только сортировка. Причина: минимальный MVP.

## 14. Совместимость и простая реализация

- Все данные могут храниться в одном локальном JSON, который init() читает и валидирует.
- UI не требует сторонних библиотек: vanilla JS + fetch к локальному файлу/модулю.
- Локализация меток дней — через простую таблицу ['Пн','Вт','Ср','Чт','Пт','Сб','Вс'].

End of CONTRACT
