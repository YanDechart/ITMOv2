# Анализ процесса: AS IS и TO BE

## AS IS

- Акторы: инженер‑ревьюер или CI‑джоб, FastAPI‑сервис, внешний LLM.
- Поток: клиент отправляет POST на `/api/reviews` c полем `diff` в произвольном `dict`; `ReviewService.review` без валидации и нормализации формирует prompt вида "Review this pull request...\n{diff}" и вызывает `llm.generate`; API возвращает `{"comment": answer}`.
- Узкие места и потери:
  - Нет валидации тела запроса и контракта ответа (формат OUT-1 не соблюдён).
  - Нет ограничения размера diff (нарушение API-1), возможны таймауты/расходы.
  - Нет удаления секретов перед LLM (нарушение SEC-1).
   - Нет таймаута и контролируемого ответа для LLM (REL-1 не реализован; конкретный HTTP‑код и формат тела контролируемого ответа в CASE.md не определены, это открытый вопрос).
  - Политика логирования не определена, риск логировать чувствительные данные (OBS-1 не реализован).


## TO BE

Один целевой процесс для первого сценария с соблюдением правил SEC-1, API-1, OUT-1, REL-1, OBS-1 и SCOPE-1.

```mermaid
flowchart TD
    Client[Клиент (ревьюер/CI)] --> API[POST /api/reviews]
    API --> Validate[Валидация тела и размера]
    Validate -->|>20000 символов| R413[HTTP 413 (API-1)]
    Validate -->|ok| Redact[Редактирование секретов (SEC-1)]
    Redact --> Prompt[Сборка prompt]
    Prompt --> CallLLM[Вызов LLM с timeout 10s (REL-1)]
    CallLLM -->|timeout/error| CtrlResp[Контролируемый ответ (REL-1)]
    CallLLM -->|ok| Parse[Парсинг и валидация OUT-1]
    CtrlResp --> Log[Лог: request_id, длительность, статус (OBS-1)]
    Parse --> Log
    Log --> Resp[JSON: summary, risks(≤3), checks (OUT-1)]

```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Ограничение длины diff | Нет | HTTP 413 при >20 000 символов (API-1) | Интеграционный тест: diff длиной 20 001 → 413 |
| Редакция секретов | Нет | Удаление/маскирование токенов/паролей/ключей перед LLM (SEC-1) | Юнит‑тест сервиса с `token=`/`password=`/ключом → в prompt остаётся [REDACTED] |
| Контракт ответа | `{"comment": answer}` | JSON {summary, risks(≤3:{file,line,evidence,risk}), checks} (OUT-1) | Интеграционный тест: 200 и схема ответа по OUT-1 |
| Таймаут и контроль ошибок LLM | Нет | Таймаут 10s и контролируемый ответ (REL-1) | Интеграционный тест с "медленным" LLM‑стабом → возвращён контролируемый результат; конкретный статус/формат не зафиксированы в CASE.md |
| Политика логирования | Не определена | Логируются только request_id, длительность, статус; diff/ответ не логируются (OBS-1) | Интеграционный/юнит‑тест: перехват логов, в сообщениях нет diff/LLM‑ответа |

## Как использовали AI

- Для чего: выровнять TO BE‑процесс под правила CASE.md и выделить точки проверки.
- Тип промпта: master prompt на ревью учебного PR.
- Строка в [`prompts.md`](prompts.md): P1-02 и раздел «Master Prompt v1».
- Что проверили и исправили сами: убрали предположения вне правил (аутентификация, SLA); добавили REL-1 и OBS-1 как обязательные; сопоставили шаги процесса с тестами.
