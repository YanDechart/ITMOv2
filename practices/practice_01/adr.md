# ADR: решение для первого рабочего сценария

- Статус: proposed
- Дата: 2026-09-11
- Ответственные: команда учебного проекта (студент)

## Контекст

Учебный сервис AI‑reviewer получает diff PR и должен возвращать структурированный результат для человека‑ревьюера и автоматических проверок. В TRAINING_PR.diff выявлены нарушения правил из CASE.md: отсутствуют редакция секретов (SEC-1), ограничение длины diff/ответ 413 (API-1), контракт ответа (OUT-1). Также упомянуты требования по таймауту внешнего LLM и контролируемому ответу (REL-1) и по политике логирования (OBS-1). Решение должно соблюдать SCOPE-1: сервис только советует и не совершает действий в репозитории.

## Решение

- Ввести предвходовую валидацию тела запроса и лимит на длину diff: при >20 000 символов возвращать 413 (API-1).
- Перед формированием prompt редактировать секреты (токены, пароли, приватные ключи) в diff по правилу SEC-1, заменяя значения на маркер [REDACTED].
- Формировать и возвращать структурированный ответ по OUT-1: `summary`, `risks` (≤3 с полями `file`, `line`, `evidence`, `risk`), `checks`.
- Применить QA-1: включать риск в ответ только если он подтверждён строкой diff или правилом репозитория; валидация поля `evidence` обязательна для каждого элемента `risks`. Проверка выполняется на стороне сервиса: `evidence` должен ссылаться на указанную строку diff (по `file`/`line`) и быть цитатой/фрагментом из неё либо однозначно ссылаться на правило из CASE.md; элементы без evidence или с неподтверждённым evidence исключать из ответа.
- Оборачивать вызов LLM таймаутом 10 секунд; в случае таймаута/ошибки возвращать контролируемый ответ (REL-1); конкретный HTTP‑статус и формат тела контролируемого ответа CASE.md не задаёт — это открытый вопрос.
- Принять политику логирования OBS-1: логировать `request_id`, длительность и статус, исключив содержимое diff и ответ модели.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Отложить структурирование ответа до позже | Без OUT-1 невозможны автоматические проверки и трассируемость рисков |
| Чанкование длинных diff вместо 413 | Не требуется в учебном кейсе; правило API-1 предписывает 413 |
| Полное хранение входов/выходов для аудита | В учебном сценарии не требуется; повышает риск утечки секретов и усложняет соответствие OBS-1 (нельзя логировать diff и ответ модели); правила CASE.md хранения не требуют |

## Последствия и главный риск

- Положительные последствия:
  - Предсказуемый контракт и воспроизводимые проверки;
  - Снижение риска утечки секретов;
  - Контролируемое поведение при деградации LLM.
- Ограничения:
  - Диффы >20 000 символов не обслуживаются данным эндпоинтом;
  - Возможна потеря контекста из‑за редактирования секретов (приемлемо по SEC-1).
- Главный риск:
  - Неверная идентификация секретов или избыточная маскировка.
- Как проверим риск:
  - Юнит‑тесты на типовые шаблоны секретов; code review правил редактирования; интеграционные тесты на отсутствие секретов в prompt и логах.
