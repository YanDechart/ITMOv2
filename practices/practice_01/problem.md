# Проблема и метрики

## Проблема

- Пользователь: инженер по качеству/ревьюер, использующий сервис для первичного анализа PR по diff.
- Ситуация: отправляет diff на эндпоинт сервиса, чтобы получить краткое резюме и риски.
- Что происходит сейчас: по учебному PR сервис вставляет diff целиком в промпт LLM без сокрытия секретов, не ограничивает длину diff и возвращает ответ не в требуемом контракте (возвращает `{ "comment": ... }`).
- Почему это мешает пользователю или бизнесу: нарушаются правила репозитория `SEC-1` (риск утечки секретов), `API-1` (нет отказа 413 для слишком длинных diff), `OUT-1` (несовместимый формат ответа), из‑за чего повышаются риски инцидентов и невозможно автоматизировать проверки/интеграции.
- Что не входит в задачу: интеграция с GitHub, изменение бизнес‑логики ревью, построение очередей/фона; фокус только на соблюдении правил `SEC-1…QA-1` для данного PR.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов в соответствии с `OUT-1` (структура summary/risks/checks) | Интеграционный тест на эндпоинт | 100% | На каждом коммите и перед релизом | Тесты API |
| Доля запросов с diff > 20 000 символов, получающих 413 | Тест с генерацией длинного diff | 100% | На каждом коммите и перед релизом | Тесты API |
| Доля случаев, когда секреты редактируются до отправки в LLM | Юнит‑тест сервиса с тестовым `token=` | 100% | На каждом коммите | Юнит‑тесты сервиса |

## Почему изменение метрики подтвердит решение проблемы

- Формат ответа по `OUT-1` гарантирует пригодность результата для автоматических проверок и потребителей.
- 413 для длинных diff по `API-1` защищает производительность и стоимость.
- Редакция секретов по `SEC-1` снижает риск утечки чувствительных данных при обращении к внешнему LLM.
