## User Scenarios & Testing (mandatory)

### User Story 1 - Посмотреть расписание на сегодня (Priority: P1)

Как студент, я открываю Mini My ITMO и хочу сразу увидеть своё имя, учебную группу и расписание на текущий день.

Why this priority: базовая ценность продукта — показать расписание «сегодня».

Independent Test: Симулировать ответы логики (success/empty/error) и проверить переходы состояний: loading → success|empty|error; порядок занятий соответствует порядку из логики (логика сортирует).

Acceptance Scenarios:
1. Given страница открыта впервые и для «сегодня» есть занятия, When UI завершает загрузку, Then отображается имя студента и группа; Then выбран день «Сегодня»; Then показывается список карточек занятий в порядке, полученном от логики (по времени начала по возрастанию).
2. Given страница открыта впервые и для «сегодня» занятий нет, When UI завершает загрузку, Then отображается пустое состояние с сообщением «На выбранный день занятий нет».
3. Given произошла ошибка получения данных, When UI завершает загрузку, Then отображается состояние ошибки с понятным сообщением и кнопкой «Повторить», доступной с клавиатуры.
4. Given отображено состояние ошибки, When пользователь нажимает «Повторить», Then UI возвращается в состояние загрузки и при успехе показывает занятия или пустое состояние.

---

### User Story 2 - Переключение между днями недели (Priority: P2)

Как студент, я хочу переключаться между днями недели, чтобы посмотреть расписание на другой день.

Independent Test: При смене дня UI должен отобразить состояние загрузки и затем соответствующее состояние; выбранный день подсвечен; фокус корректен для доступности; применяется политика latest-wins для быстрых переключений.

Acceptance Scenarios:
1. Given открыт «сегодня», When пользователь выбирает «Завтра», Then UI показывает загрузку и затем итоговое состояние (занятия/пусто/ошибка) для выбранного dayId.
2. Given выбран «Понедельник», When пользователь с клавиатуры выбирает «Среда», Then фокус/выделение обновляются, контент соответствует «Среда».
3. Given пользователь быстро кликает по разным дням, When ответы приходят в произвольном порядке, Then UI отображает данные последнего запрошенного dayId (latest-wins), игнорируя устаревшие ответы.

---

### User Story 3 - Просмотр карточек занятий (Priority: P3)

Как студент, я хочу видеть в карточке занятия название предмета, время, аудиторию и преподавателя, чтобы быстро понять, куда и когда идти.

Independent Test: Для каждого занятия отображаются поля subject, время (startTime–endTime), room, teacher; длинные значения не ломают верстку; при отсутствии room/teacher отображается «—».

Acceptance Scenarios:
1. Given у занятия есть все поля, When UI рисует карточку, Then отображаются все атрибуты в читаемом виде.
2. Given отсутствует room или teacher, When UI рисует карточку, Then значение заменяется «—», карточка валидна визуально.

### Edge Cases
- Длинные названия/ФИО/аудитории — перенос/усечение.
- Пересекающиеся занятия — порядок логики сохраняется; UI не решает конфликты.
- День без занятий — пустое состояние.
- Ошибки сети/данных — сводятся к «Не удалось загрузить расписание» с кнопкой Retry; тексты зависят от типа ошибки.
- Частично пустые данные (room/teacher) — UI показывает «—».
- Локализация времени: 24-часовой формат, ru-RU; «Сегодня» определяется по локальному времени.

## Requirements (mandatory)

### Структура экрана и элементы управления
- Header: имя студента и учебная группа.
- Контрол выбора дня недели: список дней (Пн–Вс) с подсветкой выбранного; «Сегодня» помечается UI; без горизонтальной прокрутки на телефонах.
- Область расписания: список карточек или состояния (loading/empty/error).
- Кнопка «Повторить» в состоянии ошибки.

### Functional Requirements
- FR-001: UI MUST отображать имя студента и учебную группу в шапке.
- FR-002: UI MUST отображать контрол выбора дня недели с выбранным по умолчанию текущим днём («Сегодня»).
- FR-003: UI MUST при смене дня показывать индикатор загрузки до завершения получения данных.
- FR-004: UI MUST отображать карточки занятий с полями: subject, время (startTime–endTime), room (опционально), teacher (опционально); при пустых room/teacher показывать «—».
- FR-005: UI MUST отображать занятия в порядке, полученном от логики (логика сортирует); MAY пересортировать по startTime при явной несогласованности.
- FR-006: UI MUST отображать пустое состояние, если для выбранного dayId занятий нет.
- FR-007: UI MUST отображать состояние ошибки с сообщением и кнопкой «Повторить» при ошибке получения данных.
- FR-008: UI MUST обеспечивать доступность (клавиатура, фокус, подписи, роли).
- FR-009: UI MUST быть адаптивным: без горизонтальной прокрутки на телефонах; контрол дней компактен.
- FR-010: UI MUST форматировать время в 24-часовом формате (ru-RU) с ведущими нулями (например, 08:30–10:00).
- FR-011: UI MUST сохранять выбранный dayId в пределах текущего сеанса просмотра.
- FR-012: UI MUST использовать нейтральный символ «—» для неизвестных/пустых значений room/teacher.
- FR-013: UI MUST реализовать политику latest-wins для быстрых переключений дней (обрабатывать только последний завершившийся запрос getDay).
- FR-014: UI MUST не выполнять авторизацию и не обращаться к внешним API (демо-данные локальные).

### Визуальные состояния UI
- Loading: индикатор (скелетон/спиннер); описание для скрин-ридера («Загрузка расписания…»).
- Success: список карточек; при отсутствии карточек — Empty.
- Empty: сообщение «На выбранный день занятий нет».
- Error: сообщение и кнопка «Повторить»; описание для скрин-ридера («Не удалось загрузить расписание»).

### Доступность и адаптивность
- Клавиатурная навигация: Tab/Enter/Space; Retry доступна клавиатурой.
- Видимый focus и корректный порядок фокуса.
- Масштабирование текста до 200% без поломки лэйаута.
- Брейкпоинты: телефон — одна колонка; планшет/десктоп — возможны две.

### Ожидания UI от логики (контракт)
- Формат данных: camelCase. Entities: Student{name,group}; Lesson{subject,startTime,endTime,room?,teacher?}; DaySchedule{dayId,label,lessons[],isEmpty}; WeekSchedule{days[]}.
- Day id: 1–7 (ISO-8601). UI сопоставляет «Сегодня». Абсолютные даты не требуются.
- Операции: init(), getStudent(), getWeek(), getDay(dayId), retry() — все возвращают Promise.
- Сортировка: выполняется логикой. UI использует полученный порядок.
- Пустой день: lessons = [], isEmpty = true.
- Ошибки: тип/код (LoadError, DataFormatError, ValidationError, DomainError, UnknownError); UI маппит на пользовательские сообщения.
- Retry: кнопка вызывает retry() и затем getDay(currentDayId).

### Key Entities
- Student: name, group.
- DaySchedule: dayId, label, lessons, isEmpty.
- Lesson: subject, startTime, endTime, room?, teacher?.

## Success Criteria (mandatory)
- SC-001: Индикатор загрузки появляется ≤ 0.3 сек после открытия.
- SC-002: Переключение дня завершает показ нового состояния ≤ 1.5 сек (демо).
- SC-003: 90% пользователей находят расписание «сегодня» ≤ 10 сек.
- SC-004: Нет горизонтальной прокрутки при ширине ≥ 320px.
- SC-005: 100% интерактивных элементов имеют видимый фокус и корректные подписи.
- SC-006: Пустой день всегда отображается как Empty; ошибки — с Retry.
- SC-007: При быстрой смене дней показ соответствует последнему запросу (latest-wins) в 100% случаев.

## Assumptions
- Студент аутентифицирован вне скоупа; UI не выполняет авторизацию.
- «Сегодня» определяется по локальному времени.
- Демо-данные локальные; без внешних API.
